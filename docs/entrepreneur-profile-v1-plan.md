# FindOPC 新政策匹配智能体：创业者画像 V1 实施计划

> 状态：设计稿，尚未实施  
> 日期：2026-09-20

## 1. 本轮要解决的问题

新智能体需要处理三种真实用户状态：

1. 已经确定落地地区，希望查当地政策；
2. 有几个候选地区，希望横向比较；
3. 尚未确定地区，希望先了解各地支持政策再决策。

因此，V1 不把“所在地区”作为所有用户的统一必填项，而是先判断用户的地区决策状态。

## 2. 新智能体的建设边界

本项目按全新的政策匹配智能体设计，不沿用现有 AI 助手的画像字段、交互流程、提示词和匹配逻辑。

可以复用的基础能力只有：

- 已核验的政策、案例和来源数据；
- 地区及行业标签；
- 用户登录与权限体系；
- 网站现有的政策详情和来源链接能力；
- 已有服务器、数据库和部署环境。

暂不复用：

- 现有 AI 助手页面；
- 现有研究画像；
- 现有 Agent 会话流程；
- 现有政策召回和排序逻辑；
- 现有长期研究偏好。

新智能体独立设计、开发和测试。旧智能体在替代方案完成前保持不动，避免影响网站现有功能。

## 3. V1 应当新增的字段

### 3.1 第一优先级：首屏基础画像

| 中文名称 | 字段名 | 是否必填 | 说明 |
|---|---|---:|---|
| 地区决策状态 | `locationMode` | 是 | `fixed` 已确定、`shortlist` 候选比较、`open` 开放探索 |
| 明确落地地区 | `targetRegionId` | 条件必填 | `locationMode=fixed` 时填写 |
| 候选地区 | `candidateRegionIds` | 条件必填 | `locationMode=shortlist` 时选择 2—5 个地区 |
| 当前所在地 | `currentRegionId` | 否 | 只用于估计迁移便利度，不能代替政策适用地区 |
| 行业方向 | `industryTagIds`、`industryDescription` | 是 | 选择主要行业标签，可补充具体业务描述 |
| 创业阶段 | `ventureStage` | 是 | 构思想法、产品验证、筹备落地、初创运营、成长发展 |
| 企业注册状态 | `registrationStatus` | 是 | 未注册、办理中、已注册、拟迁入 |
| 团队人数 | `teamSize` | 是 | 使用整数，判断是否符合 OPC 人数范围 |
| 政策需求主题 | `policyTopicCodes` | 否 | 七类多选，用于排序和选址比较，不直接判定资格 |
| 主要需求 | `primaryNeed` | 是 | 用户用一句话说明当前最希望解决的问题 |
| 预算范围 | `budgetRange` | 否 | 用于建议排序，不作资格硬判断 |
| 已有资源 | `existingResources` | 否 | 产品、客户、技术、算力、数据、渠道等 |

七类政策主题统一为：

1. 算力技术
2. 财政激励
3. 场景开放
4. 创业生态
5. 金融资本
6. 制度治理
7. 人才培育

### 3.2 第二优先级：注册信息

只有用户选择“已注册、办理中或拟迁入”后才显示：

| 中文名称 | 字段名 | 用途 |
|---|---|---|
| 企业注册地区 | `registeredRegionId` | 判断本地注册条件 |
| 企业成立日期 | `establishedDate` | 判断初创年限和新设企业条件 |
| 市场主体类型 | `entityType` | 判断有限公司、个体工商户等主体限制 |
| 本地经营状态 | `localOperationStatus` | 判断是否已经实际经营或准备迁入 |

### 3.3 第三优先级：动态资格答案

年龄、学历、毕业时间、人才身份、退役军人、残疾人和失业登记等信息，不放在首屏，也不一次性要求用户填写。

系统检索到候选支持措施后，如果原文包含相关条件，再动态追问并保存为：

```text
conditionAnswers
- conditionCode
- answerValue
- valueType
- relatedMeasureId
- saveConsent
```

缺少这些信息时，结果标记为“待补充信息”，不能猜测，也不能直接判断为不符合。

## 4. 三种地区模式如何工作

### 4.1 已确定地区 `fixed`

```text
目标地区 + 行业 + 创业状态
→ 检索当地、上级和国家政策
→ 匹配具体支持措施
→ 判断资格条件
```

这是新智能体首先实现的基础匹配模式。

### 4.2 候选地区 `shortlist`

```text
2—5 个候选地区 + 行业 + 核心需求
→ 分地区检索支持措施
→ 按统一维度比较
→ 用户选择一个意向地区
→ 进入详细资格判断
```

比较维度包括：可匹配措施、支持主题、明确金额或资源、缺失条件和原文来源。

### 4.3 开放探索 `open`

```text
行业 + 创业阶段 + 政策需求主题
→ 在数据覆盖较完整的地区中检索
→ 推荐 3—5 个候选地区
→ 展示推荐依据和数据覆盖范围
→ 用户选择意向地区
→ 进入详细资格判断
```

开放探索不能宣称“全国最优城市”。页面应统一显示：

> 推荐结果基于 FindOPC 当前已收录并核验的政策资料，不代表全国城市完整排名。

## 5. 地区推荐的 V1 判断方法

V1 不以“政策数量最多”直接判定地区优劣，先采用透明规则：

| 维度 | V1 作用 |
|---|---|
| 资格匹配 | 用户满足、可能满足或待补充的支持措施数量 |
| 需求契合 | 是否覆盖用户选择的政策需求主题 |
| 支持明确度 | 是否存在明确补贴、工位、算力、贷款或场景安排 |
| 支持完整度 | 一个地区覆盖的支持主题数量 |
| 证据质量 | 是否为正式、现行且来源可追溯的政策 |

地区结果必须同时展示：

- 推荐理由；
- 可匹配的具体支持措施；
- 尚需用户补充的资格条件；
- 该地区当前收录政策和措施数量；
- 数据更新时间和覆盖限制。

## 6. 与政策数据的关系

现有 71 条正式政策核验表继续作为政策级底表，不需要重新整理。

但资格匹配不能只使用整份政策，后续需要建立“支持措施表”，一行对应一项具体措施，例如：

- 算力补贴；
- 免费工位；
- 创业奖励；
- 创业担保贷款；
- 人才公寓；
- 场景订单。

每项措施至少需要：措施名称、政策 ID、地区、主题、支持对象、资格条件、支持标准、有效期、原文条款、原文链接和人工核验状态。

创业者画像字段与支持措施资格条件必须一一对应。没有措施原文依据的画像字段，不用于资格否决。

## 7. 下一步实施顺序

### 第一步：冻结字段和页面流程

- 确认本文件中的首屏字段；
- 确认三种地区模式；
- 画出首屏和动态追问的简单页面流程；
- 暂不加入年龄、学历等敏感信息。

完成标准：字段名、取值和显示条件不再频繁变化。

### 第二步：建立新智能体的独立骨架

新建独立的：

- 创业者画像页面；
- 政策匹配结果页面；
- 画像请求和返回 DTO；
- 画像存储结构；
- 支持措施查询服务；
- 规则判断服务；
- AI 解释服务。

关键变化：

- 新智能体不依赖旧 Agent 会话和旧画像；
- 画像采用 `locationMode`、`targetRegionId` 和 `candidateRegionIds`；
- 规则引擎负责资格判断，AI 不直接决定用户是否符合政策；
- 新旧智能体暂时并存，新功能完成验收后再决定是否替换旧入口。

### 第三步：建立支持措施 MVP 数据

- 从 71 条正式政策中选择 20—30 条高质量政策；
- 优先覆盖 3—5 个政策资料较完整的地区；
- 将政策拆成具体支持措施；
- 每项措施回到政策原文人工核验；
- 建立资格条件的标准编码。

完成标准：每项措施都有原文证据，可以解释为什么匹配或不匹配。

### 第四步：实现固定地区精准匹配

- 地区和行业召回候选措施；
- 规则引擎判断“已满足、不满足、待补充信息、原文未作规定”；
- AI 只负责解释结果和生成行动建议；
- 页面展示政策原文和来源链接。

完成标准：至少使用 10 个测试画像得到稳定、可复核的结果。

### 第五步：实现候选地区比较

- 支持选择 2—5 个地区；
- 按相同条件比较支持措施；
- 不用单纯政策数量决定排名；
- 展示各地区的优势、限制和缺失资格信息。

### 第六步：实现开放式选址推荐

- 只在数据覆盖达到要求的地区中推荐；
- 输出 3—5 个候选地区；
- 展示推荐依据和覆盖限制；
- 用户选中地区后转入精准匹配。

### 第七步：用户测试

至少邀请以下三类用户试用：

1. 已确定落地地区的创业者；
2. 正在比较多个地区的创业者；
3. 尚未确定地区的创业者。

重点记录：用户是否理解问题、是否愿意提供信息、推荐结果是否有帮助、哪些资格问题难以回答。

## 8. 本轮先不做

- 不一次性收集所有敏感身份信息；
- 不直接扩大到全部 71 条政策；
- 不宣称全国城市排名；
- 不让大模型直接决定政策资格；
- 不根据政策标题或摘要推测资格条件；
- 不在支持措施数据尚未完成前制作复杂评分模型。
